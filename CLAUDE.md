Цей репозиторій містить матеріали для підготовки до внутрішньої атестації PeEx (профіль Clouds - DevOps Engineer, основна платформа — AWS). Тут немає коду, лише Markdown-документація.

## Структура

```
Peex.txt                     # сирий експорт з порталу (джерело правди, не редагувати)
2026-10-09.png               # скріншот порталу (приклад NEBo Task)
README.md                    # індекс доменів + 3 приклади інфраструктури + матриця покриття
DevOps-<Домен>/DevOps-<Домен>.md   # питання домену з інфраструктурою до кожного
```

Назви папок і файлів: `DevOps - Infrastructure as Code` → `DevOps-Infrastructure-as-Code`, `&` → `and`, `CI/CD` → `CI-CD`.

## Формат файлу домену

1. `# DevOps - <Домен>` і посилання `[⬅ Назад до README](../README.md)`.
2. Таблиця-зміст: `# | Питання (anchor-лінк) | Key/Рівень | Інфраструктура (📘/🤖)`.
3. Блок легенди.
4. На кожне питання:
   - `## <ID>. <Назва>`, далі `` `Key` `` (якщо є);
   - **Description** і **Outcomes**: дослівно з `Peex.txt`; якщо Outcomes немає, пиши `_(У вихідному файлі Outcomes для цього питання відсутні.)_`;
   - `### 🏗️ Інфраструктура — 📘 NEBo Task: <назва>` або `### 🏗️ Інфраструктура — 🤖 Згенеровано Claude (не офіційний NEBo Task)`;
   - розділи: Task Description, Prerequisites, Guidance and Tips, Acceptance Criteria (Functional / Non-Functional), Outcome Artifacts, Vendor Annex.
5. Питання розділяються `---`.

## Правила

- **Маркування обов'язкове.** 📘 позначає офіційний NEBo Task, перенесений дослівно. 🤖 позначає все, що згенерував Claude. Ніколи не видавай згенерований контент за офіційний.
- Тексти NEBo Tasks не перефразовуй, змінюй лише Markdown-форматування.
- Якщо доповнюєш неповний NEBo Task, додай окремий підрозділ `#### 🤖 Доповнення — згенеровано Claude (...)` (див. CNT-2).
- Мови: службові заголовки, легенда й примітки пишуться українською; зміст тасків англійською, як в оригінальних NEBo.
- У Vendor Annex першим іде AWS, потім Azure, GCP, on-prem/generic.
- Службові поля порталу (кількість менторів, «Request NEBo Mentor») не переносяться. `Key` і рівні (Trainee/Middle/Lead) зберігаються.
- Якщо щось виправляєш чи відновлюєш у вихідних даних (наприклад, назву CICD-3), явно познач це у файлі домену та в README → «Примітки щодо вихідних даних».

## Коли додаєш чи змінюєш питання

1. Онови файл домену: таблицю-зміст і секцію питання.
2. Онови `README.md`:
   - лічильники в таблиці доменів («Питань / 📘 / 🤖» і рядок «Разом»);
   - матрицю покриття (новий рядок, підсумки по колонках A/B/C);
   - списки «Покриває (N)» в описах інфраструктур A/B/C;
   - «Рекомендований порядок», якщо змінилось покриття.
3. Перевір, що anchor-лінки відповідають заголовкам (GitHub-стиль: нижній регістр, пробіли → `-`, крапки й коми прибираються).

## Інфраструктури в README

- **A**: мікросервісна платформа на AWS EKS.
- **B**: гібридна платформа на віртуальних машинах (міграція з on-prem в AWS, HA/DR, Ansible).
- **C**: DevOps Toolkit, багатомовний репозиторій інструментів, що працює з A і B.

Мета: мінімальна кількість проєктів, які разом покривають усі питання (зараз 30/30). Нове питання спершу намагайся покрити наявними A/B/C і лише якщо це неможливо, розширюй їх.
